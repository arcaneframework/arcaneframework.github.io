Detailed Description

Sorts by uniqueId without comparing, when the uniqueIds allow it.

Same order out as sorting the ItemInternal* with CompareUniqueIdWithSuppression: suppressed items last, the others by increasing uniqueId. What changes is how that order is reached.

A uniqueId is an integer, so the order it defines can be read digit by digit rather than through n.log(n) comparisons: two linear passes per digit, and no comparison at all. The number of digits is decided at run time from the range the family actually uses, so a family whose uniqueIds span a million values pays two passes and not eight.

Three properties are tested, in this order, and each one is a fact about the data rather than an assumption about the mesh:

  1. Already in order. One linear pass, and nothing is permuted at all. An initial allocation hands out uniqueIds in creation order for at least one family, so this is not a rare case.
  2. A dense range. If the n uniqueIds cover exactly n consecutive values then they are a permutation of that range, and the sorted position of each one is its own value: a single scatter, no digits.
  3. Otherwise, the radix passes over the range's width.

A range too wide to be worth digits falls back to the comparison sort.

Ties: uniqueIds are unique, so the only items that compare equal are suppressed ones, and the caller reads only the first nbItem() entries, which hold none of them. The comparison sort was not stable either, so neither promised anything there.
