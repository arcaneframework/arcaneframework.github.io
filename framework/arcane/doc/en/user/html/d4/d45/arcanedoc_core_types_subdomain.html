The SubDomain

The ISubDomain interface (defined in arcane/core/ISubDomain.h) is the interface of the subdomain manager. It is the central object representing the local state and the execution environment of a single computation unit of an Arcane application.

What is a Subdomain ?

When an Arcane application runs in parallel, the global mesh is partitioned into several subdomains: each computation unit (an MPI rank, possibly associated with a set of threads) owns a portion of the mesh together with the local variables, modules, services, and case options associated with it. The ISubDomain instance is the handle to this local portion of the application.

The object hierarchy is as follows:

IApplication (one per executable)
└── ISession (one per computation session)
└── ISubDomain (one per (rank, thread) unit)
├── IVariableMng, IModuleMng, IEntryPointMng, IServiceMng, ...
├── IMeshMng → IMesh (default mesh)
├── ICaseMng (the .arc data set)
└── ...
  • IApplication is the process-level manager: it is shared by all the subdomains of the process (main factory, application information, resource manager, ...).
  • ISession groups one or more subdomains. In domain replication (several independent computations sharing the same processes), a session contains several ISubDomain instances, one per replica.
  • ISubDomain is where the identity of the computation unit lives: ISubDomain::subDomainId() is the rank in the parallel group of the subdomain and ISubDomain::nbSubDomain() is the size of this group.

In domain replication, ISubDomain::parallelMng() covers only the parallel group of one replica, while ISubDomain::allReplicaParallelMng() covers the group of all the replicas. Without replication, both managers are the same.

Access to the Main Managers

Most of the ISubDomain interface is made of accessors to the managers owned by the subdomain. They are grouped here by category:

Category Accessors
Data ISubDomain::variableMng() (all the IVariable instances), ISubDomain::meshMng() and ISubDomain::defaultMesh() / ISubDomain::defaultMeshHandle() / ISubDomain::meshes(), ISubDomain::propertyMng()
Structure ISubDomain::moduleMng(), ISubDomain::entryPointMng(), ISubDomain::moduleMaster() (the master module, always created)
Parallelism / threads ISubDomain::parallelMng(), ISubDomain::allReplicaParallelMng(), ISubDomain::threadMng(), ISubDomain::timerMng(), ISubDomain::timeStats(), ISubDomain::loadBalanceMng()
Time ISubDomain::timeLoopMng(), ISubDomain::timeHistoryMng()
I/O and case file ISubDomain::ioMng(), ISubDomain::caseMng() (the ICaseMng of the data set), ISubDomain::caseDocument(), ISubDomain::caseOptionsMain(), ISubDomain::commonVariables()
Protection ISubDomain::checkpointMng()
Others ISubDomain::acceleratorMng(), ISubDomain::memoryInfo(), ISubDomain::physicalUnitSystem(), ISubDomain::configuration(), ISubDomain::mainFactory(), ISubDomain::session(), ISubDomain::application(), ISubDomain::applicationInfo()

ISubDomain is therefore the place to look for anything that is "mine" in the application: my variables, my mesh, my parallel group, my case options. For a detailed description of the mesh and of the entity families it contains, refer to The Mesh and The Item Family.

Mesh-related Methods

The subdomain manages the meshes associated with the computation unit. The main methods are:

  • ISubDomain::defaultMesh() / ISubDomain::defaultMeshHandle(): the default mesh of the subdomain (named "Mesh0"). The handle always exists, even if the associated mesh has not yet been created.
  • ISubDomain::meshes(): the list of all the meshes of the subdomain.
  • ISubDomain::allocateMeshes(): allocates the IMesh instances (they are created but contain no entities). This method must be called before any other operation involving the mesh.
  • ISubDomain::readOrReloadMeshes(): reads the meshes. At startup, the meshes are read from the data set; during a restart, they are loaded from a protection.
  • ISubDomain::initializeMeshVariablesFromCaseFile(): initializes the variables whose values are specified in the data set.
  • ISubDomain::doInitMeshPartition(): applies the initial mesh partitioning (see Handling parallelism in Arcane).
  • ISubDomain::setInitialPartitioner(): sets the partitioner to use for the initial partition. The subdomain takes ownership of the instance and destroys it at the end of the computation. This method must be called before the module initialization, for example in a construction entry point.
Warning
The methods ISubDomain::mesh(), findMesh(), addMesh() and ISubDomain::meshDimension() are deprecated. Use ISubDomain::defaultMeshHandle(), IMeshMng::findMeshHandle(), IMeshMng::meshFactoryMng() and IMesh::dimension() instead.

Case File and Directories

The subdomain keeps track of the data set (the .arc file) and of the output directories:

  • ISubDomain::caseName(), ISubDomain::caseFullFileName(), ISubDomain::fillCaseBytes(), ISubDomain::setCaseName(): information on the data set. ISubDomain::setCaseName() must be called before initialization.
  • ISubDomain::caseDocument(): the XML document of the data set.
  • ISubDomain::caseOptionsMain(): the global options of the data set (CaseOptionsMain).
  • ISubDomain::commonVariables(): the "standard" variables (time, time step, ...).

Three output directories can be set (the directories must exist and the methods must be called before initialization):

  • ISubDomain::exportDirectory() / ISubDomain::setExportDirectory(): the base directory for exports (protections and restarts).
  • ISubDomain::storageDirectory() / ISubDomain::setStorageDirectory(): the base directory for exports requiring archiving. If not set, ISubDomain::exportDirectory() is used.
  • ISubDomain::listingDirectory() / ISubDomain::setListingDirectory(): the base directory for listings (logs, execution information).

Creation and Lifecycle

A subdomain is created from a SubDomainBuildInfo object, which provides:

  • the parallel manager of the subdomain (SubDomainBuildInfo::parallelMng()),
  • the subdomain index in the session (SubDomainBuildInfo::index()),
  • the data set: file name (informative) and content (SubDomainBuildInfo::caseBytes()),
  • optionally, the parallel manager of all the replicas (SubDomainBuildInfo::allReplicaParallelMng()) for domain replication.

The creation goes through ISession::createSubDomain():

SubDomainBuildInfo sdbi(parallel_mng, index);
sdbi.setCaseFileName(case_file_name);
ISubDomain* sub_domain = session->createSubDomain(sdbi);

The typical lifecycle of a subdomain is:

Phase Methods Description
Build (internal) Creation of all the subdomain managers (variable manager, module manager, entry point manager, service manager, case manager, checkpoint manager, time loop manager, ...) and of the default mesh handle.
Initialize (internal) Initialization of the accelerator, reading of the data set (validates the XML and merges the configuration), creation of the default mesh, loading of the subdomain services, creation of the master module.
Mesh setup ISubDomain::allocateMeshes(), ISubDomain::readOrReloadMeshes(), ISubDomain::initializeMeshVariablesFromCaseFile(), ISubDomain::doInitMeshPartition() Allocation and reading of the meshes, initialization of the mesh variables from the data set, application of the initial partition.
Restart support ISubDomain::setIsContinue() / ISubDomain::isContinue() Flag indicating that a restart is being performed. ISubDomain::setIsContinue() must be called before ISubDomain::allocateMeshes() so that the meshes are loaded from a protection instead of the data set.
Run (application code) The application entry points are executed through the time loop.
Destroy ISubDomain::doExitModules(), ISubDomain::destroy() Execution of the exit entry points, then destruction of all the subdomain objects (the variable manager is destroyed last, since every object may contain variables).

ISubDomain::isInitialized() / ISubDomain::setIsInitialized() indicate whether the subdomain has been initialized. ISubDomain::onDestroyObservable() allows registering a notification that is called before the subdomain is destroyed.

Getting the SubDomain from the Code

Nearly every object owned by the subdomain provides a subDomain() accessor to climb back to it:

  • services: subDomain() inherited from the service base class,
  • modules: IModule::subDomain() inherited from IModule,
  • entry points: IEntryPoint::subDomain() inherited from IEntryPoint,
  • meshes: IMesh::subDomain(),
  • variables: IVariable::subDomain(),
  • item families: IItemFamily::subDomain(),
  • case options: ICaseOptions::subDomain().

The canonical pattern inside an entry point or a service method is therefore:

void MyModule::onDoSomething()
{
IVariableMng* vpm = subDomain()->variableMng();
IMesh* mesh = subDomain()->defaultMesh();
IParallelMng* pm = subDomain()->parallelMng();
// ...
}

Key Points

  • ISubDomain is the per-replica root object of the application: anything that needs the local variables, the local mesh, the local parallel group, or the local case options goes through it.
  • It is not the application: ISubDomain::application() gives the process-wide objects. The subdomain is where the identity of the computation unit lives (ISubDomain::subDomainId() is the rank).
  • The ordering of the initialization methods matters: ISubDomain::setCaseName(), ISubDomain::setExportDirectory(), ISubDomain::setInitialPartitioner() before initialization; ISubDomain::setIsContinue() before ISubDomain::allocateMeshes().
  • The subdomain is the seam for the advanced execution modes: domain replication (several subdomains per session), restarts (protections), and direct execution (tests), which all plug in through its setters (ISubDomain::directExecution() / ISubDomain::setDirectExecution()).
