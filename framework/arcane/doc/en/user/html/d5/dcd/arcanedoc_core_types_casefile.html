Dataset (.ARC)

Introduction

This chapter describes the structure of a dataset. The dataset is an XML file that contains the values used to configure the execution of a calculation code.

Here is an example of a dataset in English:

<?xml version="1.0"?>
<case codename="ArcaneTest" codeversion="1.0">
<arcane>
<title>Sod Shock Tube</title>
<description>This dataset allows testing the simplified Hydro module of
Arcane
</description>
<timeloop>ArcaneHydroLoop</timeloop>
</arcane>
<!-- List of meshes (always in English) -->
<meshes>
<mesh>
<filename>tube5x5x100.ice</filename>
</mesh>
</meshes>
<functions>
<table name="table-dt" parameter="time" value="real" interpolation="linear">
<value>
<x>0.0</x>
<y>1.0e-3</y>
</value>
<value>
<x>1.0e-2</x>
<y>1.0e-5</y>
</value>
</table>
</functions>
<simple-hydro>
<deltat-init>0.001</deltat-init>
<deltat-min>0.0001</deltat-min>
<deltat-max>0.01</deltat-max>
<final-time>0.2</final-time>
</simple-hydro>
</case>

A dataset consists of four parts:

  • the <arcane> element, which allows, among other things, configuring the time loop and the active modules (see <arcane> Element)
  • the mesh element (<meshes>), which allows describing the mesh (see Meshes (tag <meshes>)).
  • the element containing functions (<functions> or <fonctions>) (see Functions (tags <fonctions> or <functions>))
  • the remaining elements concern the options of the different code modules.

Only the <arcane> tag is required. The other tags are optional.

Warning
Whitespace characters in attributes are forbidden in the XML standard. Therefore, the dataset is invalid if they are present. However, parsers may tolerate them. Whitespace characters at the beginning and end of tags are significant and can change the meaning or render a dataset invalid. For example, <file> Toto</file> indicates that the mesh file contains a space before the characters 'Toto'.
Note
For historical reasons, it is tolerated to have spaces at the beginning or end of a tag's text in the case of simple dataset options (see Simple Options). In this case, these spaces are ignored. For example, <deltat> 25.0 </deltat> is valid. These spaces are only allowed in module and service options, not in tags specific to Arcane (such as <arcane>, <functions>, <meshes>, ...).

<arcane> Element

This element contains information about the time loop used and the list of active modules. The content of this element is the first thing read in the dataset. The following elements are possible:

<arcane>
<title>Sod Shock Tube</title>
<description>This dataset allows testing the simplified Hydro module of
Arcane
</description>
<timeloop>ArcaneHydroLoop</timeloop>
<modules>
<module name="Hydro" actif="true"/>
<module name="PostProcessing" actif="false"/>
</modules>
<configuration>
<parameter name="NotParallel" value="false"/>
<parameter name="NotCheckpoint" value="true"/>
</configuration>
</arcane>

The following table lists the possible elements:

English elementFrench elementDescription
timeloopboucle-en-tempsName of the time loop used. This name must correspond to a time loop available in the code's configuration file.
titletitreTitle of the dataset. Purely informational.
descriptiondescriptionDescription of the test case. Purely informational.
modulesmodules

List of modules with their activation status. This tag is used to indicate whether an optional module is active or not. By default, optional modules are not active. It is a list of <module> elements as follows:

<module name="Module1" active='true'/>
<module name="Module2" active='false'/>
servicesservices

List of singleton services with their activation status (which defaults to true). It is a list of <service> elements as follows:

<service name="Service1" active='true'/>
<service name="Service2" active='false'/>
<service name="Service3"/>

In the previous example, the services named 'Service1' and 'Service3' will be loaded.

configurationconfiguration

List of configuration parameters. These parameters are not read by Arcane but can be used, for example, by the code's launch procedure. Each parameter is in the following format:

<parameter name="Param1" value='value1'/> <!-- English -->
<parametre name="Param1" value='value1'/> <!-- French -->

Meshes (tag <meshes>)

There are two ways to specify the meshes of a computation in a dataset:

  • the modern method, based on mesh services, which uses the <meshes> element. This is the recommended method and new users should use it (see Specifying Meshes with Services (tag <meshes>)).
  • the legacy method, which uses one or several <mesh> elements (or <maillage> in French). This method is obsolete and should only be used by existing codes (see Legacy Mesh Specification (tag <mesh> or <maillage>)).
Note
If both methods are used in the same dataset, the <meshes> element takes precedence: the meshes are then created by the mesh services and the legacy <mesh> elements are ignored.

Specifying Meshes with Services (tag <meshes>)

With this method, the meshes are managed by services. The <meshes> element is read by the ArcaneCaseMeshMasterService service. This element is always in English, even for a French dataset (i.e. when xml:lang="fr"), because it is read before the other options of the dataset: the meshes have to be created before the modules and the services are initialized, as the latter may require them.

The <meshes> element contains one or several <mesh> elements. Each <mesh> element is an instance of a service implementing the Arcane::ICaseMeshService interface. By default, the ArcaneCaseMeshService service is used and its options are described in the following sections (the complete and up-to-date list is also available in the page Service 'ArcaneCaseMeshService').

The meshes are named Mesh0, Mesh1, ... in the order of appearance of the <mesh> elements. The first mesh (Mesh0) is the default mesh of the sub-domain and must always be created. The other meshes may be null on some or all sub-domains (for example when a mesh-builder-customiser service is used).

Note
When several meshes are defined, a module or a service can be associated with a given mesh using the mesh-name attribute of the corresponding element of the dataset (see Service Options).

The following example specifies two meshes, the first one read from a file and the second one created by a generator:

<meshes>
<mesh>
<filename>sod.vtk</filename>
</mesh>
<mesh>
<generator name="Cartesian3D">
<origin>1.0 2.0 3.0</origin>
<x><n>100</n><length>2.0</length></x>
<y><n>15</n><length>2.0</length></y>
<z><n>10</n><length>4.0</length></z>
</generator>
</mesh>
</meshes>

Mesh Generators

The <generator> element specifies an implementation of the Arcane::IMeshBuilder interface. The name of the service is given by the name attribute. The following generators are provided by Arcane (the list of available generators depends on the compile options):

Cartesian2D — 2D Cartesian mesh generator.

If the division in X and Y is not specified, the number of subdomains must be a perfect square (1, 4, 9, 16, 25, ...). If only the division in X or Y is specified, this specified value must be a divisor of the number of subdomains.

ElementTypeDefault valueDescription
originreal2noneMesh origin.
nb-part-xinteger0Number of subdomains in X. If absent or if the value 0 is specified, the X division is calculated dynamically.
nb-part-yinteger0Number of subdomains in Y. If absent or if the value 0 is specified, the Y division is calculated dynamically.
generate-sod-groupsboolfalseIf true, groups are generated for a Sod test case (internal to Arcane).
face-numbering-versioninteger4Version of the algorithm for face numbering. Version 1 corresponds to unstructured numbering. Version 4 corresponds to Cartesian numbering.
xcomplexnoneDescription of the mesh blocks in X (at least one). See below.
ycomplexnoneDescription of the mesh blocks in Y (at least one). See below.

Cartesian3D — 3D Cartesian mesh generator.

It has the same options as Cartesian2D (with a real3 origin), plus the following ones:

ElementTypeDefault valueDescription
nb-part-x / nb-part-y / nb-part-zintegernoneNumber of sub-domains in X, Y and Z.
edge-numbering-versioninteger2Version of the algorithm for edge numbering. Only value 2 is currently valid. In this case, if edges are enabled, the maximum number of nodes is limited to 2^31.
zcomplexnoneDescription of the mesh blocks in Z (at least one). See below.

For Cartesian2D and Cartesian3D, the mesh is described by blocks in each direction. Each <x>, <y> or <z> element describes one block and can be repeated to describe several consecutive blocks:

<x>
<n>10</n>
<length>2.0</length>
<progression>1.0</progression>
</x>
ElementTypeDefault valueDescription
nintegernoneNumber of cells of the block.
lengthrealnoneLength of the block.
progressionreal1.0Geometric progression of the cell sizes inside the block.

Sod3D — Sod shock tube mesh generator (3D).

ElementTypeDescription
xintegerNumber of cells in X.
yintegerNumber of cells in Y.
zintegerNumber of cells in Z.

HoneyComb2D — 2D hexagonal mesh generator.

ElementTypeDescription
originreal2Mesh origin.
pitch-sizerealPitch value, which is the distance between two opposite sides of a hexagon. Must be strictly positive.
nb-layerintegerNumber of layers of hexagons. If 1, there is only the central hexagon. Must be strictly positive.

HoneyComb3D — 3D hexagonal mesh generator.

It has the same options as HoneyComb2D (the origin is 2D: the height values are provided by the heights option), plus the following one:

ElementTypeDescription
heightsreal[]List of cell heights. This array must have at least 2 values. The values must be increasing. The number of cell layers in height is equal to the number of elements in this array minus 1.

Here is a complete example using a generator:

<meshes>
<mesh>
<generator name="Cartesian2D" >
<nb-part-x>2</nb-part-x>
<nb-part-y>2</nb-part-y>
<origin>0.0 0.0</origin>
<x><n>5</n><length>5.0</length></x>
<y><n>3</n><length>3.0</length></y>
</generator>
</mesh>
</meshes>

Mesh Files and Readers

When the mesh is read from a file (element <filename>), the mesh reading service is automatically detected from the extension of the file. The following readers are provided by Arcane (the list of available readers depends on the compile options):

Extension(s)ServiceDescription
vtkVtkLegacyCaseMeshReaderLegacy (structured) VTK format.
vtk / vtuVtkPolyhedralCaseMeshReaderVTK/VTU format with support for polyhedral cells. Options: print-mesh-infos (bool, default false) and print-debug-infos (bool, default false).
vtuVtuCaseMeshReaderXML VTK (VTU) format.
mshMshCaseMeshReaderGmsh format.
medMEDCaseMeshReaderMED format (requires HDF5 support).
unf / mli / mli2 / ice / uns / unvLimaCaseMeshReaderLima formats (requires Lima support).

The automatic detection can be avoided and the reader configured with the <specific-reader> element. For example:

<meshes>
<mesh>
<filename>faultx4_3x3x2.vtk</filename>
<specific-reader name="VtkPolyhedralCaseMeshReader">
<print-mesh-infos>true</print-mesh-infos>
</specific-reader>
</mesh>
</meshes>

Legacy Mesh Specification (tag <mesh> or <maillage>)

Warning
This method is obsolete: it is only kept for compatibility with existing codes. New codes and new users should use the method based on mesh services (see Specifying Meshes with Services (tag <meshes>)).

With this method, the mesh information is specified with one or several <mesh> elements (or <maillage> if the language of the dataset is French, i.e. when xml:lang="fr"). Contrary to the <meshes> element, the names of the elements and the attributes of this method depend on the language of the dataset: in the following, both the English and the French names are given.

The first <mesh> element describes the default mesh (Mesh0). The additional meshes (i.e. the second, third, ... <mesh> elements) are named Mesh1, Mesh2, ... or DualMesh1, DualMesh2, ... if the dual attribute is set to true.

The following example specifies a mesh read from a file, with an internal partitioning:

<mesh>
<file internal-partition="true">mesh1.med</file>
</mesh>

The <meshgenerator> Element

The <meshgenerator> element (the name is the same in English and in French) allows generating a mesh without a mesh file. It contains one and only one of the following elements:

<cartesian> — Cartesian mesh generator. The dimension of the mesh is deduced from the presence of the <lz> elements (2D if absent, 3D if present). It accepts the following elements:

ElementTypeDescription
originereal3Origin of the mesh (only the two first components are used for a 2D mesh).
nsdinteger[]Number of sub-domains in each direction. The number of values must be equal to the dimension of the mesh.
lxrealLength of a block in X. This element can be repeated to describe several consecutive blocks. It has a mandatory attribute nx (number of cells of the block) and an optional attribute prx (geometric progression of the cell sizes, default 1.0).
lyrealSame as <lx> for the Y direction (attributes ny and pry).
lzrealSame as <lx> for the Z direction (attributes nz and prz). Only for 3D meshes.
face-numbering-versionintegerVersion of the algorithm used to compute the unique identifiers of the faces.
edge-numbering-versionintegerVersion of the algorithm used to compute the unique identifiers of the edges.

<sod> — Sod shock tube mesh generator. The dimension of the mesh is deduced from the elements present: 1D if only <x> is specified, 2D if <x> and <y> are specified, 3D if <x>, <y> and <z> are specified. It accepts the attribute zyx (bool, default false) to generate the mesh in the ZYX order, and the following elements:

ElementTypeDescription
xintegerNumber of cells in X. Optional attribute delta (real): space step in X.
yintegerNumber of cells in Y. Optional attribute delta (real): space step in Y.
zintegerNumber of cells in Z. Optional attribute delta (real): space step in Z. Optional attribute total (bool): if true, the value is the total number of layers for all the processes.
random-coefrealRandom perturbation coefficient of the nodes.

The expected syntax is for example <meshgenerator><sod><x>nx</x><y>ny</y><z>nz</z></sod></meshgenerator>.

<simple> — simple mesh generator, mainly used for tests. It accepts one element:

ElementTypeDescription
modeintegerType of mesh to generate (value between 1 and 4).

The <partitioner> / <partitionneur> Element

The value of this element is the name of the partitioning service to use for the initial decomposition (e.g. Metis, PTScotch, Zoltan). If this element is absent, the default partitioner of Arcane is used. It accepts the following attribute:

English attributeFrench attributeTypeDefault valueDescription
need-basic-partition-firstneed-basic-partition-firstboolfalseIf true, a basic partitioning is done first. This is useful for parallel partitioners (e.g. ParMetis) when some partitions would otherwise be empty.

The <tied-interfaces> / <interfaces-liees> Element

This element specifies the tied interfaces of the mesh (e.g. welds between non-conforming parts of the mesh). It contains one or several <semi-conform> elements (or <semi-conforme> in French) with the following attributes:

English attributeFrench attributeTypeDefault valueDescription
slaveesclavestringnoneName of the face group of the slave interface. This attribute is mandatory.
not-structurednon-structureboolfalseIf true, the slave interface is not structured.
planar-toleranceplanar-tolerancereal0.Tolerance for the planarity of the interface.
Note
If no tied interface is specified, the face groups named SOUDURE or SOUDURES are automatically used as tied interfaces (if they exist in the mesh).

Functions (tags <fonctions> or <functions>)

It is possible to define functions in the dataset that are used to vary the values of an option based on physical time or iteration. The set of functions is defined in the <fonctions> tag if the language is French or <functions> if the language is English.

Note
In the rest of the document, only English terms will be used to improve readability.

A function must have a unique name that is used by the option to reference it. The following example shows how to define a table-dt function and use it as a reference in the <my-option> option:

<?xml version="1.0"?>
<case codename="ArcaneTest" xml:lang="en" codeversion="1.0">
<arcane>
</arcane>
<functions>
<table name="table-dt" parameter="time" value="real" interpolation="linear">
...
</table>
</functions>
<my-module>
<my-option function="table-dt">0.01</function>
</my-module>

Functions take a single argument as a parameter and can return the type expected by the option that uses them. The two possible values for the parameters are:

  • physical time. In this case, the parameter type is a real.
  • iteration number. In this case, the parameter type is an integer.

At the beginning of each iteration, Arcane automatically updates the dataset options that reference a function (via the method ICaseMng::updateOptions()).

The <functions> tag allows defining two types of functions:

  • lookup tables specified directly in the dataset. These are continuous or piecewise linear functions.
  • external functions written in C#. In this case, any type of function whose signature matches the type expected by the option can be defined. Chapter Using C# functions for the dataset indicates how to define and use these functions.

Lookup Table Syntax

A lookup table is a continuous or piecewise linear function defined by a set of (X,Y) pairs. For example:

<!-- Example in English -->
<functions>
<table name="table-dt" parameter="time" value="real" interpolation="linear">
<value><x>0.0</x><y>1.0e-3</y></value>
<value><x>1.0e-2</x><y>1.0e-5</y></value>
</table>
</functions>
<!-- Example in French -->
<table nom='test-time-real-2' parametre='temps' valeur='reel' interpolation='lineaire'>
<valeur> <x>0.0</x> <y>3.0</y> </valeur>
<valeur> <x>4.0</x> <y>9.0</y> </valeur>
<valeur> <x>5.0</x> <y>7.</y> </valeur>
<valeur> <x>6.0</x> <y>2.0</y> </valeur>
<valeur> <x>10.0</x><y>-1.0</y> </valeur>
<valeur> <x>14.0</x><y>-3.0</y> </valeur>
</table>

The (X,Y) pairs must be sorted by increasing value of X. If the parameter value is smaller or larger than the first or last value of the lookup table, the last value is taken. In the previous example for the lookup table test-time-real-2, if X<0.0 then 3.0 is returned, and if X>14.0 then -3.0 is returned.

Lookup tables have the following attributes:

English NameFrench NameTypeDescription
nomnamestringName of the lookup table.
parameterparametrestringParameter type. Possible values are time (temps in French) for a parameter that is physical time or iteration for a parameter that is the current iteration number.
valuevaleurstringType of the lookup table return value. Possible values are real, integer, real3, string, or bool (respectively reel, entier, reel3, string, and bool in French).
interpolationinterpolationstringPossible values are linear or constant (lineaire or constant-par-morceaux in French). If the interpolation is constant, the returned value is the corresponding Y value that matches the X immediately below the parameter value. If the interpolation is linear, a linear interpolation is performed between (X1,Y1) and (X2,Y2), where X1 is the value of X immediately below the parameter and X2 is the next value in the lookup table. For the previous lookup table (test-time-real-2) example, if X equals 4.5, then 9.0 is returned if the interpolation is piecewise constant, and 8.0 (i.e., Y1 + (X-X1)*(Y2-Y1)/(X2-X1) <=> 9.0 + (4.5-4.0)*(7.0-9.0)/(5.0-4.0)) if the interpolation is linear.
comulcomulstringMultiplier coefficient for the value. This attribute is optional and must be of the same type as the function's value. If present, the function's value is multiplied by the value of this attribute (for a Real3, the multiplication is done component by component).
deltat-coefdeltat-coefrealMultiplier coefficient for physical time. This attribute is optional and is used to multiply the current time step value (see ICaseMng::updateOptions()).
